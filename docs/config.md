# thimble's config

thimble's agents take their settings from `~/.thimble/config.json` (`$THIMBLE_HOME/config.json` when THIMBLE_HOME is set). With no file, every agent runs on the defaults below. A workspace can override any key but `browser`, `cardWait`, `askKey` and `extensions` in `workspaces/<workspace>/config.json`. Objects merge key by key, and `null` means thimble's default.

The Settings pane writes this file for the models and efforts, the fast mode of the classifiers and of `thimble fix`, the permission mode of an extension's program that runs the dev agent, the feature switches (`features`, `views.propose` and `agents.cardCheck.auto`) and the Ask key choice (`askKey`). `/config` → thimble in Claude Code writes the same feature switches, and the two stay in step. Each change goes to the file the value came from, so a key the workspace's file sets is changed there. Edit the file by hand for everything else. A change applies to the next start of an agent, with no restart of Claude Code.

Your Claude Code session and thimble's agents edit this file and a workspace's `config.json` under your session's permission mode, as any file outside the folder you opened. A session thimble runs on its own, such as an extension's program or `thimble fix`, asks you before it edits them, and one with nobody to ask can't. A permission mode of `"bypass"` counts as Manual (`permissionMode` below).

thimble changes none of Claude Code's settings files. The orientation, its critic, the writers, view builds, view reviews, report checks and code tickets are subagents of your Claude Code session: they run in its permission mode, and thimble adds no rules or sandbox to it. Only `thimble fix` and an extension's program that runs the dev agent keep a permission mode and a sandbox of their own (the `dev` entry).

```json
{
  "sandbox": { "use": "when-available", "enforce": false },
  "browser": "system",
  "agents": {
    "orientation": { "model": "claude-opus-5-5", "effort": "xhigh", "data": "ask" },
    "writer": { "web": "off" },
    "dev": { "web": "off" }
  }
}
```

If the file isn't valid JSON, or a key or value is unknown, no agent starts. The Settings pane and `thimble doctor` show the error, which names the file and the key. `thimble doctor` also prints which file is read and which browser is used.

## Top-level keys

| Key | Values | Default | What it does, and the risk |
|---|---|---|---|
| `installs` | `"ask"`, `"deny"`, `"allow"` | read and ignored | Earlier versions sent each command that installs software to you. Such commands now follow your Claude Code session's permission mode, as every other command does: thimble adds no rule for them. |
| `sandbox.use` | `"when-available"`, `"never"` | `"when-available"` | Runs the Bash of `thimble fix` and of an extension's program in Claude Code's sandbox where it can run (Linux needs bubblewrap and socat; `thimble doctor --verbose` names the commands). Your own session and thimble's agents are not affected: they follow your Claude Code settings. In a development install, thimble's server commits a code ticket's change to its branch. The ticket's checks, and the copy of thimble the server screenshots before and after the change, run in thimble's sandbox runtime (Anthropic's sandbox runtime, installed with thimble; it needs Node 20.11 or later, and on Linux bubblewrap, socat and ripgrep): no network, no view of your home folder, and writes only to the ticket's worktree and its cache. The edited code first runs outside a sandbox once merged into your install, so just before that thimble asks "Apply this change to thimble's own code?", in every permission mode, Bypass and Auto included, and merges only on your Allow, and only the change it named; otherwise the change stays on its branch. `thimble fix` asks the same in the terminal. Where the sandbox runtime can't run (`thimble doctor --verbose` says why), a ticket's checks run outside the sandbox, so thimble also asks before the ticket starts. `"never"` turns the sandbox off for `thimble fix` and extension programs. |
| `sandbox.enforce` | `true`, `false` | `false` | `false` runs `thimble fix` and an extension's program without the sandbox where it can't run: `thimble fix` asks you in the terminal first, and thimble shows a notice the first time an extension's program runs without one, since it can read what you can, thimble's token among it. `true` refuses to start them there, and says why. |
| `browser` | `"system"`, `"bundled"`, `"off"` | the system browser when one is found, else Playwright's Chromium if installed, else off | The browser for screenshots: card checks, view checks and reviews, and the screenshot tool. `"system"` uses Chrome, Edge or Chromium installed on the machine. `"bundled"` uses the Chromium that the installer downloaded. `"off"` takes no screenshots, so cards and views are checked without pictures and graphics aren't repaired. Only in the file in thimble's home. Run `thimble restart` after changing it. |
| `cardWait` | minutes, a number above 0 and up to 720 | `10` | How long a code ticket's card waits for your answer to thimble's questions about its own code: whether the change may be applied, and, where the sandbox runtime can't run, whether the ticket may start. A question nobody answers in that time is a no, and the card says so, with the wait. Requests of your session and of thimble's agents, a ticket's agent among them, are never declined on a timer. A change applies to the next card. Only in the file in thimble's home. |
| `askKey` | `"meta"`, `"alt"`, `null` | `null`, which is `"meta"` | The key you hold while you click something in the browser to ask about it: `"meta"` is ⌘-click on a Mac and Ctrl-click elsewhere, `"alt"` is ⌥-click on a Mac and Alt-click elsewhere. The other key places a card freely on the canvas while you drag it. Settings' Ask key choice writes it. Only in the file in thimble's home. |
| `views.propose` | `true`, `false`, `null` | `null`, which is on | Whether thimble proposes views (the "View proposals" switch). After each of your messages, when a side thread answers and when an orientation ends, a row above the prompt (and a card above the browser's reply box) may propose a view, and opening a file only Raw can show may propose a viewer for its type. Nothing builds until you accept. Deciding whether to propose takes one model call on a copy of your session's context, on the `suggest` row. `false` turns view proposals off: the proposal's Don't ask again writes it, and Settings' View proposals switch and `/config` → thimble → "View proposals" write it and take it out. |
| `features.<key>` | `true`, `false`, `null` | `null`, which is on | thimble's feature switches, below ([Features](#features)). |
| `extensions.<name>.enabled` | `true`, `false` | `true` | `false` switches the extension off in every workspace. `thimble extension off <name>` writes it and `thimble extension on <name>` takes it out. Settings → Extensions switches one off for a single workspace. Only in the file in thimble's home. |

## Features

Each of thimble's features can be turned off. `/config` → thimble in Claude Code and the browser's Settings show the same
seven switches, and a change in one shows in the other. Off, a feature runs nothing in the background. Three keys live
in `features`; View proposals is `views.propose` above, and Card check is `agents.cardCheck.auto` below.

| Switch | Key | Default | Off |
|---|---|---|---|
| View proposals | `views.propose` | on | No view proposals after your turns. |
| Labels | `features.labels` | on | Claude's guidance leaves labels out, `apply_label` refuses with a line that says the switch is off, and the panel has no Labels section. |
| Checks | `features.checks` | on | No check runs by itself, on answers, cards or documents; `run_check` refuses; no tints on answers and no Checks section. |
| Citation marks | `features.citationMarks` | on | The terminal draws citations as plain links, with no ✓ or ×, and checks none. |
| Coverage | `features.coverage` | on | No coverage line under answers, no Coverage section, and no background count of the records. |
| Card check | `agents.cardCheck.auto` | on | No card check after Claude makes or edits a card; Check the card in its details still runs one. |

A switch that changes Claude's guidance (Labels, Checks) sends the guidance again at Claude's next request.

## Agents

`agents` has one entry per agent:

- **`orientation`**: the orientation. Its `data` and `web` set to `"off"` also hold for your Claude Code session and every one of thimble's agents, since thimble's plugin refuses those calls, and its `subagentModel` and `subagentEffort` set `thimble:orient-helper`, the type the orientation starts its own subagents as
- **`critic`**: the critique of the orientation, which runs when the orientation asks for a review of its analysis with its `critique` tool
- **`writer`**: the report writers
- **`checks`**: the report checks
- **`dev`**: view builds, view reviews and code tickets, each a subagent of your session, and `thimble fix`
- **`labels`**: the label classifier, and the call that checks whether an extension's view fits a corpus
- **`cardCheck`**: the card check's reading of a card's picture
- **`suggest`**: the view proposals: the check for one after each of your messages, after a side thread answers and after an orientation ends, and the call that proposes a viewer for a file type
- **`refusal`**: the model and effort a classifier's call runs again on when its own model refuses it

Each agent runs on exactly the model and effort its entry gives, the defaults included, unless `/thimble:orient` or a start tool names another model or effort for one run. None of them takes your own Claude Code model or effort. The launcher unsets `CLAUDE_CODE_EFFORT_LEVEL` (passing it on as your session's own effort), `CLAUDE_CODE_SUBAGENT_MODEL` and `CLAUDE_CODE_SUBAGENT_MODEL_FORCE` in the session it starts, and blanks them there where an `env` block of your Claude Code settings sets them, which your session's effort then follows too. thimble's single model calls run without them, so that none can change what runs. Your organization's managed settings rank above thimble's, so a variable an `env` block there sets still applies.

`labels`, `cardCheck` and `suggest` are single model calls with no tools, so they take only `model`, `effort`, `fast` and `prompt`. Each runs at exactly the model, effort and fast mode Settings shows for its row (`labels`: Opus 5.5 at low effort, fast mode off; `cardCheck`: Opus 5.5 at high effort, fast mode on; `suggest`: Opus 5.5 at medium effort, with the 1M-token window when your session's context needs it). When a call's model refuses it, it runs once more on the `refusal` row's `model` and `effort` (Opus 4.8 at high effort), or not again when that row is off. The check for a view proposal after a turn does not run again: when Claude's safeguards block it, a notice says so, with Try again and Turn off view proposals. When an extension's program runs one of their tasks ([agents.md](agents.md)), they also take `network`, `data` and `env` for that program. It has no thread to ask you in, so with `data` at `"ask"` it can't edit the corpus. Set `data` to `"allow"` to let it.

An extension's agent has the entry `"<extension>:<agent>"`, such as `"swarm-orient:swarm-reader"`. It runs as a subagent of the orientation, in your session and its permission mode, so it takes only `model`, `effort`, `web`, `network` and `prompt`. Its `model` and `effort` default to those its extension's `agent.json` gives it, else the orientation's subagents', its `web` defaults to `"off"` and its `network` to `"on"`. They can only take away what the orientation's allow. With `web` off it has no web tools. With `network` off while the orientation's is on, it has no Bash, since all agents in a session share one sandbox network. Its `prompt` replaces the extension's prompt file for it. Settings has a row for each agent of the extensions running in the workspace, where its `model` and `effort` can be changed. An extension's `agents/orientation/agent.json` prompt is not an agent: it adds to the orientation's instructions, or replaces them, and the orientation keeps its own settings (`agents.orientation`).

| Key | Values | Default | What it does, and the risk |
|---|---|---|---|
| `model` | a model id, such as `"claude-opus-5-5"` | per agent: the orientation uses your own Claude Code `model`, else Opus 5.5 | The agent's model. |
| `effort` | `"low"`, `"medium"`, `"high"`, `"xhigh"`, `"max"` | per agent: `"xhigh"` for the orientation | Higher efforts use more tokens. A stored `"ultracode"` reads as `"xhigh"`. A model without effort levels, such as Haiku, runs with none. |
| `fast` | `true`, `false` | per agent: on for `cardCheck` and `dev` | Fast mode, on models that have it, for `labels`, `cardCheck` and `suggest`, and `dev`'s for `thimble fix`, the one job of thimble's server that runs Claude Code itself. A view build, a review and a code ticket run without it, since Claude Code gives a subagent no fast mode of its own. Read and ignored for the other agents, which run without a fast mode of their own. |
| `permissionMode` | `"manual"`, `"auto"` | `null`: your Claude Code session's mode, but Manual while your session runs in Bypass | Only for `dev`: the permission mode of an extension's program that runs the dev agent. Manual asks you about each call that isn't already allowed. Auto lets Claude Code's classifier decide. `"bypass"`, which earlier versions offered, counts as Manual: no program of thimble's skips its permission prompts. Code tickets and view builds don't read this row: they are subagents of your session and run in its mode. Settings shows its row only where an extension runs the dev agent with a program of its own. Read and ignored for every other agent, since thimble's agents, code tickets' among them, run in your Claude Code session's mode. |
| `web` | `"ask"`, `"off"`, `"allow"` | `"ask"`; `"off"` for `dev` | WebFetch and WebSearch. The orientation's `"off"` refuses WebFetch and WebSearch to your session and every agent; `"ask"` and `"allow"` both leave them to your permission mode. The dev agent's and the classifiers' own `web` keep their meaning. |
| `network` | `"off"`, `"on"` | `"on"` | Network access for Bash. It doesn't apply to your session or thimble's agents, which use your network as your Claude Code settings allow. `dev`'s sets it for `thimble fix`; a code ticket's agent has your session's network. Each agent's own, the orientation's included, sets it for an extension's program that runs the agent or one of its tasks, `"on"` where the agent sets none. thimble's own critic, writers and checks don't read theirs, since they run in your session. `"on"` lets Bash reach the network, as far as your own Claude Code sandbox settings allow. |
| `sandbox` | `"on"`, `"off"` | `"on"` | Only for `dev`, and for an extension's program that runs an agent: `"off"` runs `thimble fix`'s Bash, or the program, outside the sandbox, so it can write anywhere you can, and `sandbox.enforce` then doesn't stop it. thimble's own orientation, critic, writers and checks don't read it, since they run in your session. |
| `data` | `"ask"`, `"allow"`, `"off"` | `"ask"` | Edits of files in the corpus. The orientation's `"off"` refuses edits of the corpus by the file tools of your session and every agent; `"ask"` and `"allow"` leave them to your permission mode. Shell commands follow your permission mode either way. `dev`'s sets them for `thimble fix`. Each agent's own, the orientation's included, sets them for an extension's program that runs the agent or one of its tasks, `"ask"` where the agent sets none. thimble's own critic, writers and checks don't read theirs, since they run in your session. |
| `env` | a list of environment variable names, such as `["OPENAI_API_KEY"]` | `[]` | Variables of thimble's server that an extension's program running this agent or one of its tasks gets, such as the API key of a harness that brings its own model. A program gets no other variable of yours. thimble's own agents don't read it. |
| `memory` | `"inherit"`, `"on"`, `"off"` | `"inherit"` | Whether the agent reads CLAUDE.md files. `"off"` leaves them out of its context; `"on"` and `"inherit"` give it the CLAUDE.md files your session reads. |
| `prompt` | a file path, or `null` | `null` | Replaces the agent's prompt file from thimble's `prompts/` folder (`orient.md`, `critic.md`, `writer.md`, `check.md`, `dev.md`, `labels.md`, `card-check.md`). Copy the original and edit it. It is filled in the same way, and relative paths are resolved from the config file's folder. A replacement prompt can drop the rules that keep an agent within its task. |
| `auto` | `true`, `false`, `null` | `null`: on | Only for `cardCheck`: whether the card check reads each new card by itself (the "Card check" switch). With `false`, a card is checked only when you click Check the card or Check again in its details. A card shows the check only for a real problem it found, as a red ✕ at its takeaway; a fix is applied in place, with Undo in the card's details, and a fix that leaves all the card shows as it was is one more version in the card's History. |
| `subagentModel` | a model id, or `null` | `null`: the orientation's model | Only for `orientation`: the model of `thimble:orient-helper`, the type the orientation starts its own subagents as. A subagent it starts as another type, such as general-purpose or Explore, runs on the orientation's own model and effort. |
| `subagentEffort` | `"low"`, `"medium"`, `"high"`, `"xhigh"`, `"max"`, or `null` | `null`: the orientation's effort | Only for `orientation`: the effort of `thimble:orient-helper`. |

## What stays as it is

- Your own Claude Code session keeps its permission mode and your settings, whether you start it with `claude` or `thimble`. thimble adds no rule, working directory or sandbox to it, and approves none of its own tools.
- thimble's plugin refuses Claude's file tools any read or edit of `server.json` in thimble's home, which holds the token of thimble's local API, of `session.key` beside it, which proves which of thimble's sessions a call comes from, of `paired.json`, which holds a hash of each signed-in browser's cookie and of the key of its path, and of the `links` and `open` folders, which hold one-time sign-in codes, comparing the paths they resolve to. Once thimble is on in a session, a shell command that names these files literally is refused too. Another shell command can still read them, as can a Grep from a folder above thimble's home; in Manual mode such a command asks you first. The token reads what thimble's server serves, as thimble's command does, but changes only what thimble's hooks, plugin and command change: everything you do in thimble's browser, and everything it shows, needs that browser's sign-in, which the press's one-time code gives ([Signing in](../INSTALL.md#signing-in)), and each new sign-in shows a notice with Sign it out. [Permissions](../INSTALL.md#permissions) shows how to keep shell commands from these files with Claude Code's sandbox. An extension's program that runs an agent gets a token of its own instead, valid only for that agent's tools and only while it runs ([agents.md](agents.md)).
- Card code, an extension's code among it, runs in the notebook kernel as your user, with your network, whatever `network` and `sandbox` say.
- The kernel runs in Anthropic's [sandbox runtime](https://github.com/anthropics/sandbox-runtime), which thimble installs (it uses Seatbelt on macOS and bubblewrap on Linux). The kernel reads the corpus, the workspace and the system, and writes only in the workspace, apart from its views, the card types and extensions thimble found there, which your session's and the orientation's prompts are made from, and the `trusted` folder, which holds the files thimble's hooks trust (`subagents.json`, `callers.jsonl`, `launch.json`). It can't read your home folder, thimble's config, other workspaces or your Claude Code login. It keeps the network, so it can also reach local services, thimble's own API among them. Without Node, the kernel runs in bubblewrap directly on Linux, with the same limits, and unsandboxed on macOS and on Linux where bubblewrap can't create a sandbox; `thimble doctor` says which. A card check's revision runs on the kernel without asking you. `"kernel_wrap"` in the workspace's `settings.json` picks one: `"srt"`, `"bwrap"` or `"none"` (no sandbox). A workspace set to a sandbox that can't run gets no kernel.
- `thimble fix` runs only in a development install (a git clone of thimble), while the server is down, and only in a terminal: it asks you there before its change is applied, and before it starts too where the sandbox runtime can't run. While it works nobody can be asked, so it runs its Bash unasked, in the sandbox where it can run.
- Earlier versions kept the agents' models and permission modes in each workspace's `settings.json`. These settings are moved to that workspace's `config.json` the first time it is read, so each workspace keeps running as before. The old *View builds* permission row is now the dev agent's row. If the two rows were different, the stricter one is kept.
- Earlier versions of this file also gave each agent a permission mode and `fast`, and set `installs`. Those this page marks as read and ignored load without an error, `thimble doctor --verbose` lists them, and saving Settings drops them. Each agent's `network`, `data`, `sandbox` and `env` stay, since an extension's program that runs the agent reads them.
